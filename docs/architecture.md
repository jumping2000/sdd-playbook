# Plugin architecture

*Versione italiana: [architecture_IT.md](architecture_IT.md)*

Design document **as built** (version 0.12.0): choices, structure, contracts between files and limits.

## Goal and success criterion

Guide the developer through the cycle of the [playbook](playbook-ai-software-lifecycle.md), turning every phase into a
skill with an explicit human gate and, wherever possible, an executable check instead of a prose instruction.
The plugin is done well if:
1. on an empty repository `sdlc-init` produces `AGENTS.md`, `scripts/verify.py`, VS Code task, `docs/` structure and CI;
2. every skill produces a verifiable artefact (file, test, script result), not just text in the chat;
3. the same content works in Claude Code and in Codex, on native Windows and Linux;
4. working with the skills does not require repeating the playbook to the agent.

## Architecture choices

| Topic | Choice | Reason |
|---|---|---|
| Content unit | **Skill** (`SKILL.md` with `name` and `description`) | The Agent Skills format is shared by Claude Code and Codex |
| Packaging | One repository, **two manifests** (`.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`) on the same skills | One body of content, two entry points |
| Checks | **Deterministic Python scripts** in the project's `scripts/` | A check that runs is worth more than a prose rule; CI and VS Code use them without the plugin |
| Where scripts live | In `skills/sdlc-init/scripts/`, copied into the project by `sdlc-init`, with the plugin version on line 2 | Fixed path (`python scripts/...`) for both agents; the project stays verifiable without the plugin |
| Portability | Standard library only, no shell commands, argument lists | Native Windows included |
| Context | `SKILL.md` under 150 lines; templates in `references/` | Context is a scarce resource |
| Human gates | Every skill that produces a document to approve ends with **STOP**; approvals carry name, date and hash of the approved content (which lapses if the content changes); the real approval is merging the design PR into protected `main`, which the agent cannot do with a separate identity | Playbook principle 5; the agent can write text fields, not a merge |
| Proportionality | Levels **S/M/L** declared in the spec (and in its hash), with criteria partly checked on the diff (`diff_scope.py`) | The same process for one line and for a migration creates ceremony on the former and too little attention on the latter (REVIEW A6) |
| External control | The CI generated by `sdlc-init` runs the process checks on PRs (`spec_lint --base`, `diff_scope`, `trace_check --junit`, `secrets_check`) with scripts and `AGENTS.md` protected by CODEOWNERS | Every input in the branch can be changed by the agent; CI on the PR runs outside its reach |
| Effectful skills | `sdlc-loop` prepares but does not launch; commits only when authorized, never on `main` | Limit the damage of an autonomous agent |
| Agent-specific parts | Claude Code: subagent `sdlc-reviewer` (read-only tools) and opt-in hooks. Codex: none (review in a new session) | The skills stay the same; only the orchestration changes |
| Documentation coherence | The playbook is **generated** from the plugin files (`tools/build_playbook.py`), in English and Italian; tests check cross-references in both languages | Scripts, templates and documentation cannot silently diverge |
| Language | Documentation in English and Italian (`_IT` suffix); skills, templates and script messages in Italian | The file contracts (field names read by the scripts) are in Italian and must not change with the language of the docs |

Some skills read files of other skills through relative paths (`../sdlc-init/scripts/`, `../sdlc-sync/references/`): the
skill folders must stay siblings.

## State machine (`state.py`)

```
no AGENTS.md / verify.py ................................ sdlc-init
existing code, no map and no spec ....................... sdlc-map-codebase
no active spec .......................................... sdlc-spec
several active specs, no choice (branch or --spec) ...... scegli (the user decides)
--- for the chosen spec ---
spec in-revisione ....................................... sdlc-spec
spec draft, not approved or with invalid hash ........... sdlc-spec
--- level S: no plan, no review.md -----------------------
tasks.md missing ........................................ sdlc-tasks
open T-nn or T-Rnn tasks ................................ sdlc-implement
review.md "non conforme" (if present) ................... sdlc-review-diff
T-DOC open, otherwise ................................... sdlc-docs, sdlc-sync
--- levels M (default) and L -----------------------------
plan missing, not approved or lapsed .................... sdlc-plan
tasks.md missing or based on another plan ............... sdlc-tasks
closed test task without "test approvati:" .............. sdlc-tests-from-ac
open T-nn or T-Rnn tasks ................................ sdlc-implement   (consider sdlc-loop)
review.md missing or without a valid outcome ............ sdlc-review-diff
review "non conforme" without T-R ....................... sdlc-review-diff (create the T-R tasks)
review "non conforme" with all T-R closed ............... sdlc-review-diff (repeat the review)
level L without "Revisione umana del diff" .............. sdlc-review-diff
T-DOC open .............................................. sdlc-docs
otherwise (T-SYNC open or state not implemented) ........ sdlc-sync
```

The chosen spec is the one given with `--spec`, the one whose folder name appears in the current branch, or the only
active one. A spec with `Stato: implemented` or `superseded` is no longer active. Unverified bugs are reported separately
(`sdlc-bugfix`): the human decides the priority.

## File contracts

The scripts read a few fields with fixed conventions. Field names are Italian and are part of the contract. If a template
changes, the script that reads it must change too (the tests check this).

| File | Fields and structures read | Script |
|---|---|---|
| `spec.md` | title `# SPEC-<id>: ...` (date + slug equal to the folder, or a number); `- Livello:` (`S`, `M`, `L`; M if missing; read from the header only; part of the hash); `- Stato:` (`draft`, `approved`, `in-revisione`, `implemented`, `superseded`); section `## Revisioni` (mandatory with an entry if `in-revisione`); `- Approvata da / data:`; `- Hash: sha256:...` of the body (from the first `## ` section); sections `## Problema e obiettivo`, `Scope`, `Requisiti`, `Acceptance criteria`, `Domande aperte`; line `**Non-scope (esplicito):**`; `- REQ-nnn`; `- AC-nnn [REQ-nnn]`; marker `[ASSUNZIONE]` | `spec_lint`, `state`, `trace_check`, `sync_check`, `diff_scope` |
| `plan.md` | `- Approvato da / data:`; `- Basato su spec:` (hash of the spec); `- Hash:` of the body; section `## Componenti e file da creare/modificare` with lines `- path: ...` (path = first word or text in backticks); section `## Strategia di test ...` with the exact AC IDs and, if present, the `Dove` column | `spec_lint`, `state`, `diff_scope` |
| `tasks.md` | `- Basato su piano:` (hash of the plan); lines `- [ ] T-nn ...` with the fields `verifica:` (command in backticks) and `copre:` (AC IDs), without placeholders; lines `- [ ] T-Rnn ...` from review problems (`verifica:`, `copre:` optional); `T-DOC`, `T-SYNC`; `— test approvati: <name, yyyy-mm-dd, sha>` on closed test tasks (levels M and L; sha = approved `Test-Lock` commit); the marker `atteso: rosso` (case-insensitive) on test tasks defines the **red phase** (last closed `T-nn` task with the marker, next one open) | `spec_lint`, `state`, `loop`, `sync_check`, `diff_scope`, `Stop` hook |
| git commits | trailer `Test-Lock: T-nn` on the commit of the red tests: locks its test files and anchors the approval | `diff_scope` |
| test files | `# SPEC-<id>` in the file plus `AC-nnn`, or citations `SPEC-<id>/AC-nnn` (in function names `SPEC_<id with _>_AC_nnn`); `TODO`/`FIXME`/`XXX` lines ignored | `trace_check`, `sync_check` |
| folders `docs/specs/<id>/` | `<id>` = date + slug (`2026-10-24-export-csv`), equal to the title ID; old `NNN-slug` still valid | `spec_lint`, `state` (branch association) |
| JUnit XML report (`reports/junit.xml`) | `testcase` with `name`, `classname`, `file` and children `failure`, `error`, `skipped` | `trace_check --junit`, `sync_check --junit`, `loop --junit` |
| `review.md` | `- Esito:` (`conforme`, `conforme con riserve`, `non conforme`); `- Decisione di:`; `- Revisione umana del diff:` (level L) | `state`, `sync_check` |
| `docs/bugs/BUG-*.md` | `- Stato:` (`aperto`, `diagnosticato`, `corretto`, `verificato`); sections of `bugfix-template.md`; tickable items in `## Chiusura` | `bug_lint`, `state` |
| `docs/system/<area>.md` | `- Ultimo allineamento:`; `- Specifiche collegate:`; sections `## Comportamento attuale`, `Vincoli e punti delicati`, `Test di caratterizzazione` | `sync_check` |
| `docs/system/mappa.md` | presence only | `state` |
| `AGENTS.md` | lines `- Non modificare: a, b` and `- Aree sensibili: a, b` (require level L), paths in backticks or first word; read from the merge-base | `diff_scope` |
| `PROMPT.md`, `progress.md` | `PROMPT.md` read in full and passed on stdin | `loop` |
| `scripts/verify.py` | list `STEPS` | (adapted by `sdlc-init`) |
| `scripts/*.py` | line 2 `# sdlc-playbook: <version>` | `sdlc-init` (update), coherence tests |
| manifests and lockfiles (`package.json`, `pyproject.toml`, `*.csproj`, ...) | file name only | `diff_scope` (level, dependencies without plan or ADR) |
| `.secrets-ignore` | one glob per line, `#` for comments | `secrets_check` |

A field with a `<...>` placeholder or empty counts as **not filled in**.

## Differences between Claude Code and Codex

| Aspect | Claude Code | Codex |
|---|---|---|
| Skills | yes, invoked with the plugin prefix | yes (Agent Skills format); manifest in `.codex-plugin/` |
| Subagent `sdlc-reviewer` | yes | no: the review happens in a new session with the same instructions |
| `Stop` and `PreToolUse` hooks | yes, opt-in with environment variables | not provided |
| Loop | `claude -p` by default | `--agent "<command>"`: non-interactive mode and permissions to verify |
| Project context | `CLAUDE.md` with `@AGENTS.md` | reads `AGENTS.md` |

## Security and supply chain

- The skills instruct the agent and the scripts run with the user's permissions: distribute the plugin from an internal
  repository, with mandatory review, a pinned version per project and updates through PRs.
- No script downloads or runs code from the network. `docs_check.py --run-examples` runs only explicitly marked Python blocks.
- The hooks are inactive by default and are not a sandbox. The guard also blocks on an unreadable event (fail-closed). The
  loop requires an isolated environment, separately configured permissions (example: `settings.loop.json`, which also
  denies writes to the loop's checks and rules) and a feature branch; it never pushes.
- Security of the produced code (REVIEW A7): `secrets_check.py` as a `verify` step and as a final check of the loop; new
  dependencies only in the approved plan or with a new ADR (`diff_scope.py`); dependency audit documented per stack, not
  included (it needs the network).
- Prompt injection: `PROMPT.md` and the reviewer treat repository content as data; the real defence is the absence of
  secrets and of network and push permissions in the agent's environment.
- The CI generated by `sdlc-init` uses actions pinned by major tag (`checkout@v6`, `setup-python@v6`, on Node 24): in
  regulated contexts pin them by SHA.

## Limits and unverified points

- **Status:** the plugin is in design and has not been used on a real project; formats and contracts may still change
  without compatibility.
- **Windows:** suite run on Windows 11 (Python 3.13, cp1252 console) up to 0.8.0, then only in the CI matrix; the tests
  of `run.sh` with minimal PATH and fake interpreters run only on POSIX.
- **Real agents:** the skills have not been executed by a real agent on a project; the deterministic checks have (tests
  on temporary repositories, loop with a fake agent, hooks with the expected JSON input).
- **Codex:** manifest and skill invocation not validated with Codex tools; subagent support not verified.
- **Claude Code hooks:** exit code 2 as a block and the JSON format are the expected ones, not observed in a session. The
  command goes through `sh hooks/run.sh`: on Windows it requires Claude Code to run hooks with a shell that finds `sh`
  (Git for Windows); not verified in a real session.
- **Approvals:** the hash stops unintentional drift, not an agent that recomputes the hash and rewrites the field.
  Against that, the merge into protected `main` with a separate identity (`spec_lint.py --base`) and the CI process
  checks are needed: branch protection and CODEOWNERS must be configured on the platform, the plugin provides only the
  templates.
- **Red phase, `Test-Lock` and `test approvati:`:** they rely on conventions (task markers, commit trailers) the agent
  could misuse; `diff_scope.py` ties the approval to the `Test-Lock` SHA, but `test approvati:` remains text the agent can
  write: the control it cannot bypass is the code-owner review of `tests/` in the implementation PR.
- **JUnit report:** it tells which tests ran and with which outcome, not that the report belongs to that commit: it must
  be generated by `verify` in the same pass (in CI, by a job the agent does not control). Case-to-file attribution uses
  `file` and `classname`: with reporters that do not fill them in, qualified citations are needed.
- **`claude -p` from stdin:** reading the prompt from stdin with `-p` must be verified on the version in use.
- **Heuristics:** `diff_scope.py` depends on the `- path: ...` format of the plan and, for the level, counts files and
  recognizes manifests by name: it does not understand whether a public interface changed; `trace_check.py` finds IDs by
  text (qualified per spec) and does not understand test semantics; without `--junit` it does not check that tests run
  and pass; `scan_repo.py` is an inventory; none of them replaces reading the code.
- **Guard and secrets:** the guard analyses commands by words and segments, but a purpose-built command (variables,
  `eval`, scripts written to file) bypasses it; `secrets_check.py` recognizes only known formats and does not read the git
  history.
- **Reviewer:** without Bash it cannot run tests or commands; it receives diff and outputs in the message, so it judges
  what it is given. Same model as the implementer unless a different `model:` is set in the frontmatter (not verified in a
  session).
- **Scope:** the plugin does not cover release, infrastructure security, observability and operations (playbook §8),
  does not configure the agent's permissions (it provides an example for the loop) and does not approve on behalf of the
  human.

## Tests and coherence

`python -m unittest discover -s tests -v`. Besides the tests of the scripts (on temporary git repositories), of the loop
(with a fake agent that ticks one task per run) and of the hooks, the **coherence tests** check that:
- every `SKILL.md` has valid frontmatter, `name` equal to the folder and fewer than 150 lines;
- every cited `python scripts/<x>.py` exists and every script is documented, in both languages;
- every skill is in both READMEs, both skill references, both quick guides and both playbooks, and every cited skill exists;
- every cited `§` exists as a playbook heading, and the two playbooks have the same section numbering;
- both playbooks are up to date with the embedded files (`tools/build_playbook.py --check`) and contain no version references;
- every document exists in English and Italian, and each README links to the other language;
- manifest, changelog and README versions match, and every script carries the same version on line 2;
- the reviewer has no write tools, the loop example permissions deny push and writes to the checks, and the CI actions do
  not use versions on Node 20;
- the relative links of the documentation are valid (`docs_check.py`).

## Possible evolutions

Release and operations (playbook §8), integration with issue trackers, a marketplace file for Codex, multi-repository
analysis, an English version of skills and templates. They are neither documented nor implemented in this version.
